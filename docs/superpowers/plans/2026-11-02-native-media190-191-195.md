# Optional native playback boundary — 190 / 191 / 195

Prepared 2026-11-02. Current issue bodies were read in full after the native-scope
rewrite. This is a proposed application-side implementation batch, not a new
WebCore media API or a format-completeness promise.

## Concrete boundary

One owned native playback session supplies video frames and synchronized sound
to one application window. Existing `rv_host_bind_d3d11_texture`,
`rv_host_native_texture_changed` and the existing owner-thread frame acquisition
remain the complete renderer boundary. Captions are ordinary native DOM text
chosen from application-supplied timed cues using the provider's presentation
time. The renderer does not decode, fetch media, select codecs, maintain an audio
graph or own an OS media session.

Windows first: an optional SDK-only application adapter owns an
`IMFMediaEngine` in frame-server mode. That mode delivers video to the application
while the same engine renders audio; no separate audio clock or sink is added.
Use `MF_MEDIA_ENGINE_DXGI_MANAGER` with the application D3D device. On an owner
render turn, `OnVideoStreamTick` yields a presentation timestamp; only a new frame
is transferred into an owned texture. Publish the texture under the existing
key0 → render/flush → key1 protocol, notify the host, and acquire/present the host
frame. The host's keyed-mutex wait remains bounded. A paused session retains the
last frame without advancing captions. Seek invalidates pending-frame/cue
generation. No render-thread sleep, busy loop or callbacks directly into WebCore.

The SDK permits selecting the DXGI output format. Actual support for the exact
RGBA8 texture required by #176 must be measured with red/blue controls. If it is
not supported, stop with that specific result and propose a bounded existing
D3D video-processor conversion; do not reinterpret BGRA as RGBA or silently add
a CPU readback path.

`ISystemMediaTransportControlsInterop::GetForWindow` binds transport controls to
the owned top-level HWND. It publishes actual stopped/playing/paused/error state
and only supported play/pause/stop/seek actions. Its event tokens are revoked on
close. Worker callbacks enqueue a generation-tagged command to the application
owner loop; stale queued commands cannot touch a disposed host/session. No
AirPlay, remote playback, PiP, browser activation or permission policy is added.

## Ownership and error behavior

The application owns COM/MF initialization, media source, playback engine,
callback object, DXGI manager, device/texture/mutex, OS event tokens and its cue
list. The renderer retains its existing texture reference only while bound.
Close is idempotent: disable/revoke OS handlers, invalidate callback generation,
stop admission, unbind on the host owner thread, shut down the media engine,
release outstanding textures/callbacks, balance owned MF/COM initialization.
External initialization is not shut down by this adapter. Host document
replacement, element removal and device loss detach or rebind explicitly.

Provider unavailable, unsupported file/format, missing audio endpoint, device
loss and playback failure retain the actual HRESULT and explicit outcome. A
missing optional provider never becomes renderer initialization failure.
Application code supplies a local file or owned byte stream; URL fetching,
decoding algorithms, resampling, encoding, DRM and arbitrary caption parsing
stay outside this batch. No dependency or import is added to WebCore.dll or the
lean native package. Optional consumer/test linkage uses the installed Windows
SDK OS libraries only. Other OS adapters remain unqualified, not simulated.

## Proposed implementation checkpoints

1. SDK-only provider + deterministic local fixture. Own
   `examples/NativeMedia/WindowsPlayback.h` (or small cpp pair) and
   `tests/media/windows_provider.cpp`. Exercise create/open/play/pause/seek/end,
   native audio/video engine state, new-frame timestamps, exact output format,
   missing provider/source, repeated close, late callbacks and independent
   sessions. A small checked-in fixture has original generated content and a
   hash; no runtime encoder/download dependency. Qualify one actual supported
   local video+audio format first. Do not infer a codec list from the API name.
2. Existing renderer integration. `tests/media/windows.py` builds only the
   optional consumer, then feeds actual decoded video into #176's existing
   texture path. Read imported GPU pixels at three DPI scales, resize, clip,
   scroll, transform, opacity and stacking. Verify timestamp-to-cue boundaries,
   paused-frame stability, seek generation, detach/reload/host close, bounded
   keyed-mutex waits and reference cleanup. Provider audio must actually start
   and stop; audio-clock/output proof is separate from mere GetCurrentTime.
   Use an available endpoint/loopback control when possible and retain explicit
   unavailable evidence otherwise; no fabricated audible-success claim.
3. Application-window OS controls. Add a narrow optional SMTC adapter and tests
   for real HWND registration, truthful state/metadata, transport action delivery
   into the same session and token revocation/late-action refusal. An actual OS
   integration control is required; directly calling a callback alone is only
   a dispatch unit test. Register a canonical optional Windows consumer probe;
   tests fail on actual errors and record provider absence explicitly.

No protected producer rebuild is needed: all code is an application/test
consumer of the already-reviewed renderer API. Use immutable native runtime
copies, owned output, bounded jobs/slots and input/output hashes. No package,
ABI, version or kind allocation is proposed. The initial supported provider is
Windows x64; Linux/macOS providers are separate open qualification work, using
application/OS facilities rather than forcing a cross-platform media library
into the renderer.
