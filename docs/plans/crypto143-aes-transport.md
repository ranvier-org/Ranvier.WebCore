# AES transport implementation

Codex. Continue from accepted common c396; preserve HMAC declarations/layouts and the frozen Windows integration. Private engine exports only; no public ABI, package or generated kind allocation.

1. Pin the new typed C11/C++20 layout with a missing-header RED and actual compiler GREEN. Separate CBC/CTR/GCM records carry dictionary presence independently of empty bytes. AES generation and optional HMAC target-import parameters carry IDL ranges as uint32 values for explicit validation. Octet JWK stores independent presence for every supported field.
2. Add the complete private raw AES behavior route before implementation: primary CBC/CTR/GCM/KW fixtures, metadata, raw/JWK import/export, authenticated failure/padding, allowed tags/counters, copied inputs, cross-context retained keys and wrapping/teardown. The existing accepted runtime must fail at the missing AES export. Preserve the old unfiltered HMAC regression route.
3. Reuse the existing owner-thread key/operation registry and deferred completion. Add immutable JWK result snapshots owned by their operation. Copy snapshot data before releasing it; imported key material never retains its caller's spans. Wipe bridge-owned result/temporary buffers; pinned backend-owned key/input storage retains its existing destruction semantics.
4. Normalize IDL enum/range/presence separately from algorithm/key/usage validation, following SubtleCrypto's order. Algorithm names are case-insensitive; JWK constraints use exact spelling. Required missing IV/counter/CTR length differs from provided empty values. CBC uses backend PKCS7; GCM covers all seven tags and non-96-bit IV; CTR covers length1..128/counter16 and repetition rejection; KW uses RFC3394, never KWP.
5. Wrap through the target key's generic export, then KW's dedicated method or CBC/CTR/GCM encryption fallback. Unwrap reverses that flow and imports the requested AES/HMAC target. Enforce wrap/unwrap permissions independently of encrypt/decrypt, and extractability before export. Use script-free typed JWK/JSON conversion; no product JSGlobalObject/VM is introduced.
6. Obtain an explicit producer window, build only private objects/SO with hashes and exact replacement checks, and replay full AES plus HMAC/Data/serialization regression. Linux's independent backend qualification stays in its separate files; it does not replace transport validation. Root/acceptance review and all-platform qualification precede public integration.

## Evidence and remaining work

The old accepted HMAC-only runtime fails at the missing `ranvier_crypto_aes_supported` symbol before AES behavior. The new DTO layout passes actual C11 and C++20 compilation, including the unchanged HMAC layout. The first private Windows source compile found the new snapshot's missing allocator annotation and private Vector `data()` access; the corrected source compiles against the completed OpenSSL producer without diagnostics. No AES link or runtime result is claimed by these checks.

The behavioral route consumes all six published CBC/CTR examples, all 33 selected CAVP GCM records (including the one-byte IV rows), and all six RFC3394 cases. It also checks generation, typed JWK ownership, missing versus empty parameters, permissions, copied inputs, retained keys, cancellation, owner teardown, and cross-document use. It preserves the unfiltered HMAC route separately. Full transport replay is pending a new private producer window.

The current [WebCrypto JsonWebKey dictionary](https://w3c.github.io/webcrypto/#dfn-JsonWebKey) uses string-valued `key_ops`. The pinned WebKit enum-valued dictionary differs. Actual Chrome 156 controls accept unrecognized `key_ops` strings alongside a requested recognized usage and reject duplicate strings with DataError. The bridge checks duplicates before reducing to the pinned engine's recognized usage bitmap; requested `keyUsages` remains an enum and rejects unknown names with TypeError. The same controls report DataError for malformed unwrapped JWK JSON, primitive JSON and null `key_ops`. These are measured installed-browser controls, not pinned final browser acceptance. The remaining typed/JSON JWK matrix must preserve any browser/spec differences explicitly.

Linux's independent backend qualification found a real GCrypt CBC padding-zero acceptance bug. That lane owns the separate 0063 backend correction; this transport does not mask backend padding errors or replace backend qualification.
